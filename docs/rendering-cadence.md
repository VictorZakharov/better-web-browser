# Display cadence and GPU Canvas publication

Animation callbacks use the active native window's monitor frequency. Windows display configuration supplies the original rational frequency, including fractional and high refresh rates. Dynamic-refresh paths use their validated physical target mode instead of the lower virtual idle frequency. Enumeration happens on monitor or display changes, not in the frame loop. Current display settings are the fallback; 60 Hz is used only when neither native source supplies a valid frequency. There is no upper FPS policy limit.

The renderer receives cadence separately from CSS viewport geometry. A cadence-only update retimes pending rendering work without dispatching `resize`, rebuilding layout, or resetting a Canvas. Each animation batch gets one monotonic timestamp, cancellation remains effective within a batch, and callbacks requested during that batch wait for a future opportunity. Delayed delivery skips missed opportunities. Author timers retain their existing delays and cannot cancel the private rendering task.

This is an embedding rendering policy, not a promise that every callback reaches the display. The [HTML rendering model](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering) leaves opportunities dependent on hardware, visibility and application work. Benchmark `display_cadence` records the scheduling input explicitly; it does not report completed GPU work or actual screen FPS.

WebGL2 presentation uses three bounded shared GPU surfaces, under the existing process-wide 64 MiB slot budget. A private shared context resolves multisampling, flips rows and converts alpha to exact premultiplied RGBA8 bytes. Private GL bindings, framebuffer state, queries and transform feedback never enter the author's rendering state.

The producer keeps the keyed write mutex while the private copy is in flight. GLES fences order author work before the copy and subsequent author clears/writes after it. A zero-timeout client wait publishes the read key only after completion. Flush alone does not make a frame safe for external D3D access. The [GLES sync contract](https://registry.khronos.org/OpenGL-Refpages/es3/html/glClientWaitSync.xhtml) defines this completion boundary. The pinned ANGLE D3D11 implementation shares one ordered command stream; server waits do not wait on the CPU.

Pending export is distinct from unsupported export. It retains the previous displayed image rather than forcing a CPU readback or removing the bitmap. One display-paced retry per document polls all pending canvases, including applications that stop requesting animation frames. Hidden documents suspend these wakeups. Completed sequence numbers prevent an older completion from becoming the latest frame; pending slots and the latest completed fallback frame cannot be rewritten.

Only accepted submissions retire an unpreserved drawing buffer. Later completion polling does not retire it again. Public `readPixels`, `getImageData`, bitmap exports and `drawImage` continue reading the actual current drawing buffer independently of the retained displayed image. CPU presentation repair completes queued copies and recovers the newest submitted image, even after the author buffer was implicitly cleared. Resize, loss and teardown finish pending private work before destroying its surfaces; these exceptional paths may synchronize, ordinary frame publication does not.

Validation separates callback scheduling, completed GPU pixels and native presentation. Small deterministic workloads check actual rows, alpha, author state, ownership, repair and lifecycle behavior before timing. Hidden benchmark windows start at desktop origin instead of inheriting Windows' cascading placement across monitors; the cadence report records which frequency was used. Gameplay checks use the same scene, quality, canvas size and lobby state as the reference. Final timing comparisons run sequentially, rotate candidate/reference order and retain individual samples and outliers; shared-machine elapsed time is not isolated CPU cost.
