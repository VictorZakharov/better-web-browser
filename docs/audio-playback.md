# Live Web Audio playback

Breeze's native renderer owns a private audio rendering thread and V8 realm. It renders the existing graph processors in 128-frame quanta and submits stereo PCM16 through the bounded graph transport to a separate contained media process. XAudio2 owns the device voice; submitted byte buffers remain alive until the voice finishes them. Game JavaScript, layout, fullscreen changes, and painting can delay document tasks without stopping sample generation. This follows the separate control and rendering threads in the [Web Audio processing model](https://webaudio.github.io/web-audio-api/#rendering-loop).

Document task checkpoints publish graph controls and acquired immutable assets. Pending graph snapshots coalesce; assets commit atomically with their graph and stay bounded. The rendering realm retains source positions, automation, feedback delay lines, and processor histories between edits. Page callbacks never execute in that realm. Completion events, resume promises and legacy ScriptProcessor callbacks return through document media tasks; a late ScriptProcessor block becomes silence while the rest of the graph continues. Microphone packets and requested analyser/compressor observations use bounded data transfers. Closing or navigating retires the contained output generation without waiting on the document thread. OfflineAudioContext renders in its owning realm; embedders without a native output binding retain the explicit PCM admission interface.

Completed scheduled sources release their playing references after the whole quantum, including feedback-delay writes. Silent gain, stereo-panner, splitter, and merger branches belonging only to that voice stop consuming render work. Biquad and IIR histories keep their existing tail rules before retirement. Logical connections remain available to retained author handles; connecting a reused processor activates its downstream branch again. Destination input references do not keep completed sources alive. Automation-curve accounting is released after the parameter is collected, while author-retained curves remain charged. These choices follow [Web Audio node lifetime and dynamic lifetime](https://www.w3.org/TR/webaudio-1.0/#AudioNode-lifetime).

While running, `currentTime` identifies the next unrendered quantum, including progress already represented by PCM retained after backpressure. A new short source must not be scheduled into that completed PCM. Suspended contexts freeze their clock; a stream that was never acknowledged does not advance it. See [BaseAudioContext.currentTime](https://www.w3.org/TR/webaudio-1.0/#dom-baseaudiocontext-currenttime).

The output reply includes submitted source frames, consumed source frames, playback state, and observed underruns. The renderer extrapolates a started voice from its latest device sample, bounded by frames actually submitted to the device, and includes waiting transport frames in its queue estimate. The audio thread targets 120 ms of queued audio and retains the exact pending PCM on backpressure. Device priming uses three buffers before playback starts. PCM chunk, transport, and native queue byte limits remain bounded. See [XAudio2 streaming](https://learn.microsoft.com/en-us/windows/win32/xaudio2/xaudio2-streaming-audio-data) and [source-buffer ownership](https://learn.microsoft.com/en-us/windows/win32/api/xaudio2/nf-xaudio2-ixaudio2sourcevoice-submitsourcebuffer).

Complete-file decoding and AudioBuffer allocation allow at most 256 MiB per buffer, enough for ten-minute stereo music at 44.1 or 48 kHz. Immutable source snapshots allow 512 MiB per context for overlapping music sources. Encoded Web Audio inputs allow 32 MiB, enough for a ten-minute 320 kbit/s MP3; concurrent decode jobs remain limited to two. Media streaming keeps its separate 8 MiB encoded allowance, and container complexity limits remain in force. A stereo 48 kHz buffer uses 384,000 bytes per second: the old 16 MiB limit admitted only about 44 seconds. Complete-file AudioBuffers and their immutable snapshots consume memory proportional to duration; longer continuous audio belongs on the streaming media path.

For headless device checks, `scripts/run-hidden-benchmark.ps1 -AudioOutputProbe` selects the real audio endpoint with final output volume fixed at zero. It requires hidden benchmark mode; ordinary benchmark runs keep their silent output. Media volume edits cannot unmute the probe. With a diagnostic selector, reports contain bounded, periodic `Web Audio output` frame/underrun observations. The owned `audio-voice-churn.html` fixture exercises repeated finished voices, looped audio, animation, and an optional controlled author-task interruption. These observations distinguish real device starvation from a silent benchmark's graph correctness checks.
