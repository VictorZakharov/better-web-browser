# Web Crypto randomness

Breeze implements the randomness portion of [Web Cryptography Level 2](https://w3c.github.io/webcrypto/#crypto-interface)
in document and dedicated-worker realms. This is not a claim of full Web Crypto support:
`SubtleCrypto`, keys, encryption, signing, hashing, and derivation remain unimplemented.

## Contract

- `crypto` has stable identity and a `Crypto` prototype; direct construction and invalid
  method receivers throw `TypeError`.
- `getRandomValues` fills the entire byte view of all nine integer typed-array types,
  including signed and BigInt types, and returns the original view. Bytes outside the
  selected offset/length remain unchanged.
- The 65,536-byte limit is enforced in JavaScript and independently before allocation at
  the native boundary. Exceeding the public quota throws `QuotaExceededError` without mutation.
- Non-view values fail Web IDL conversion with `TypeError`; floating-point arrays and
  DataView fail the integer-type requirement with `TypeMismatchError`. Shared and resizable
  backing buffers are rejected because the IDL does not allow them. Empty/detached integer
  views are returned without requesting entropy. These rules follow
  [Web IDL buffer conversions](https://webidl.spec.whatwg.org/#es-buffer-types).
- Validation uses captured intrinsic slot getters, not replaceable `length`, `buffer`,
  `byteLength`, constructor, or toStringTag properties. Neither randomness method calls
  `Math.random`; UUID generation also ignores a replaced public `getRandomValues` method.
- `randomUUID` emits lowercase version-4 UUIDs with the required version and variant bits.
  It is exposed for the currently supported trustworthy document/worker origins (HTTPS,
  numeric loopback, local files, and blob URLs with a trustworthy tuple origin). Public HTTP
  and opaque origins do not expose it; `getRandomValues` remains available there.
- `localhost` names are conservatively excluded until transport guarantees loopback-only
  resolution, as required by [Secure Contexts](https://www.w3.org/TR/secure-contexts/#localhost).
  Inherited about:blank origins and nested ancestor security checks need explicit realm
  metadata if those browsing-context features are added; URL strings must not substitute
  for that metadata. This change does not add a general `isSecureContext` implementation.
- Native provider failure throws `OperationError`; no partially generated bytes escape and
  there is no weak-random fallback.

## Provider and provenance

The native bridge uses [rust-random/getrandom 0.4.3](https://docs.rs/getrandom/0.4.3/getrandom/)
with its default OS backend and no optional features. It selects `ProcessPrng` on supported
Windows versions and an appropriate OS entropy source on other supported targets. The
existing Windows bindings provided BCrypt but did not supply a portable randomness API for
the cross-platform engine/fuzz build. The small provider avoids maintaining a separate
entropy implementation for every platform.

The upstream source, Windows backend, and MIT/Apache-2.0 licensing were reviewed before
adding the dependency. It was already locked in the separate fuzz tooling graph; the browser
and fuzz locks now include the direct engine dependency. Release notices are generated
from the updated locked Windows graph. No third-party test code was copied.

## Regression evidence

The original `tests/fixtures/crypto-randomness.js` fixture runs unchanged in both Window and
Worker. The pre-fix document implementation failed 11 of the initial 15 checks: high bytes
were zero, BigInt assignments threw, limits and type validation were absent, and page-defined
getters/Math.random controlled execution. All 15 worker checks failed because crypto was absent.
The final fixture adds a detached-view check, for 16 checks per realm.

The final fixture passes in V8 document/worker tests, in the hidden Windows AppContainer
renderer, and through a real worker loaded by the hidden browser. Headless muted Chrome
152.0.7977.83 passes the same fixture with no browser or profile-cleanup errors. Native tests
also cover rejected counts, a deterministic full-byte-range provider, provider failure,
and trustworthy-origin classification; realm tests check secure-only UUID exposure.
Byte-lane/noncollision smoke assertions catch the old defects but are **not** a statistical
proof of randomness quality. Cryptographic strength comes from the OS provider, not the fixture.

This defect was found while investigating failed media refill requests. It is independently
incorrect and security-relevant, but a causal connection to live YouTube seek failures has
not been established. See [media seek evidence and limits](media-source-seeking.md).

Two fresh-profile, hidden/silent release retests of `972vfNAiz5M` on September 12 still
failed after ten seconds of playback followed by the player's 50% key seek to 601.533 s.
They painted 298 and 297 frames respectively, all before seeking, then the site reset the
player. The first screenshot confirms the error surface; neither run had a JavaScript
error or renderer exit. Thus successful harness execution and these API tests do not mean
that the reported playback incident is fixed.
